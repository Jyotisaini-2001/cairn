Loop — the teammate that never drops the thread

A Slack-native AI agent with long-term memory, Jira reflexes, and full observability — running on any model provider you point it at. Today: MiniMax M3.

The pitch · 90 seconds

Say this to the judges

Problem. Teams make decisions in Slack and lose them in Slack. Bugs get described in a thread, then someone has to re-type them into Jira, guess the priority, and hunt down who owns it. The knowledge evaporates; the busywork stays.

What Loop does. Loop lives inside the conversation. Mention a bug and it stages a Jira ticket — title, priority, project, and the assignee resolved from a first name to a real Jira account. Say "remember this" and it's stored with provenance: who said it, where, and when. Ask "what did we decide about the database?" weeks later and it answers — even if you phrase it completely differently, because recall is semantic, not keyword.

Why it's different. This isn't a wrapper around one vendor. The provider is an environment variable — Anthropic, MiniMax, OpenAI, Bedrock, Ollama — same brain, your choice of muscle. And it's built like a production system, not a demo: every interaction writes structured telemetry, every model call and tool call is traced, the model's own reasoning is persisted for audit, and a golden-set eval suite gates every feature.

The line to land. "Slack AI answers questions about your workspace. Loop does the work that comes out of the conversation — and shows its receipts."

Bug → staged Jira ticket

Regex gate catches bug language instantly, a focused model call extracts title / priority / owner / project, a dedup search checks for an existing ticket, then Loop posts the staged ticket and waits for confirmation.

"ishan" — a bare first name — is resolved through the workspace member list to an email, then to a Jira accountId. Nobody typed an email. Unresolvable name? Filed unassigned with a visible flag — it never guesses.

@Rasputin_Loop yes
(as a reply, in the staged ticket's thread)

Confirm → real ticket, assigned

The staged ticket is created via the Jira REST API: project resolved against live projects (a typo'd project falls back safely instead of erroring), Slack IDs in the description rewritten to human names, link posted back.

Human-in-the-loop by design — the agent proposes, a person disposes. Judges care about that.

@Loop remember: we're going with Postgres for the events service, decided in today's standup

Durable memory with provenance

Stored in a hybrid store: SQLite FTS5 (BM25) fused with a libSQL vector index (local fastembed embeddings, no API key) via reciprocal-rank fusion. Author, channel, team, and date are stamped automatically.

Recall cites its source: "per @alice in #infra on 2026-06-20 …"

@Loop what did we settle on for the events database?

Semantic recall across wording

"Settle on" never appears in the stored memory — the vector leg finds it anyway; memories are auto-injected into context before the model answers, so recall is passive, not a tool the model must remember to call.

Ask the judges to rephrase the question themselves — it still lands.

Ambient PM mode

A background daemon finds threads that went quiet without resolution and posts one polite, context-aware nudge — with a re-nudge guard, per-scan cost caps, and a channel allow-list.

It may suggest a Jira ticket but never files one on its own — restraint is a feature.

Mental map · what we know we know

Knowns, known unknowns, unknowns

Knowns

Verified live this session, with request-ids in the logs.

  • Both apps (Loop + Rasputin_Loop) connect and answer; bot identities self-register at startup.
  • Bug → stage → confirm → Jira create works end-to-end: KAN-22 filed live, assigned to "ishan" from the bare name (unknown names → unassigned, never a default email; the "reporter" is always the API token's owner — Jira auth semantics).
  • Model reasoning is captured again (thinking blocks must now be requested — fixed) and persisted per turn.
  • Hybrid memory saves + semantically recalls with provenance; channel isolation holds (verified after fixing an eval artifact that faked a leak); vector DB healthy.
  • 46/46 unit tests green; golden set 26/29 (89.7%) on MiniMax M3 after the runner was fixed to score truthfully — the 3 misses are two known M3-nondeterminism flakes plus one case that exposed (and now guards) staging-vs-create escalation. Secrets never committed to git history.
Known unknowns

Named risks — go measure before submission.

  • The ghost process. An old Loop instance on another machine shares the Rasputin token and answers ~half of events with pre-fix code. Rotate the app-level tokens to evict it, then re-verify.
  • Marketplace review: Socket Mode apps and multi-workspace OAuth have listing requirements Loop hasn't been tested against (org-wide install, event scaling, privacy policy URL, support channel).
  • MiniMax M3 tool-calling reliability on rare phrasings (the deterministic bug-gate exists precisely because prompts alone were flaky).
  • Memory at scale: recall quality past a few thousand entries is unmeasured; near-duplicate (re-phrased) memories still accumulate.
  • Ambient mode etiquette in a busy workspace — nudge frequency is capped but unmeasured against real traffic.
Unknowns

Where surprises will come from — watch these seams.

  • Endpoint drift: MiniMax silently changed how thinking is delivered once already; any compatible-API vendor can drift again.
  • Conversation history is shared per app: the agent's raw chat history spans all channels/users until restart. Memory recall is channel-scoped; history is not — the privacy seam to close before multi-workspace distribution.
  • Concurrent-team behavior: memory scoping is per-channel/team, but true multi-tenant isolation (per-workspace DBs, authz) is designed, not built.
  • Long-running process health: reconnect storms, Slack rate limits, SQLite contention under real multi-channel load.
  • Prompt-injection via message content or attachments into the agent's tool calls — guardrails block risky Slack methods, but the surface is broader than that.

Before demo day

The do-not-skip checklist

30 minutes that save the demo

  • Rotate the app-level tokens (both apps) → evicts the ghost process. Then auth.test and one smoke mention.
  • Rotate every secret that was ever shared in chat: Slack bot tokens, MiniMax key, Jira API token.
  • Run exactly one loop process. Check ps first. Watch the log while demoing.
  • Decide ambient: CAIRN_AMBIENT=off for a tight demo, or on with a 0-hour stale window for the wow moment — never both apps at once.
  • Never git checkout / stash while the app is running (DBs are untracked now, but the habit matters).
  • Pre-create the demo channel, invite both bots, verify Event Subscriptions (app_mention, message.im) on both apps.

Judge Q&A · likely questions, ready answers

Ammunition

"How is this different from Slack's built-in AI?"
Slack AI reads your workspace; Loop acts on it — files the ticket, tracks the commitment, remembers the decision — and it's self-hosted, so conversation data never leaves your infrastructure.
"What happens when the model hallucinates a ticket?"
It can't file one — creation requires a human "yes" in-thread. And every turn's reasoning is persisted, so you can audit exactly why it proposed what it proposed.
"Why should we trust the memory?"
Every memory carries provenance — author, channel, date — and recall cites it. It's not an embedding soup; it's an auditable record.
"What's the moat?"
Provider-agnosticism plus the production harness. The agent is ~15 small files; the value is the eval suite, tracing, guardrails, and memory design around it — the parts demos usually skip.
"What breaks first at scale?"
Honest answer: SQLite under multi-workspace write load and memory recall precision past ~10k entries. Both have named migration paths (per-workspace DBs, reranking) — see the roadmap in progress.md.
